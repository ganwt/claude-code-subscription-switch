# 阶段一 / 阶段二：环境调查与方案设计

日期：2026-10-25。本文只记录调查结论和推荐方案，不含任何凭证值。

证据等级标记：
- **[文档]** 官方文档已确认（code.claude.com/docs）
- **[本机验证]** 在本机实际运行验证过
- **[假设]** 尚未验证的技术假设，阶段三开头先做实验
- **[不可行]** 当前 Claude Code 能力下无法实现

## 1. 环境调查结果

### 1.1 两套独立的 Claude Code 环境 [本机验证]

| 项目 | WSL (Ubuntu) | Windows 原生 |
|---|---|---|
| CLI | `~/.local/bin/claude` → `~/.local/share/claude/versions/2.1.299`（native 安装） | 未安装 |
| VS Code 扩展 | `~/.vscode-server/extensions/anthropic.claude-code-2.1.310-linux-x64`，自带 `resources/native-binary/claude` 2.1.310 | `anthropic.claude-code-2.1.310-win32-x64`，自带 `claude.exe` 2.1.310 |
| 配置目录 | `~/.claude`（WSL 用户目录） | `%USERPROFILE%\.claude` |
| 登录状态 | `authMethod: claude.ai`，已登录 | `authMethod: claude.ai`，已登录 |
| `~/.claude/settings.json` | 无 hooks、无 apiKeyHelper、无 statusLine | 同左，只多了 permissions |
| `ANTHROPIC_API_KEY` | 未设置 | 未设置 |

要点：
- Remote-WSL 模式下扩展运行在 WSL 侧，用的是**扩展自带的 Linux 二进制**，不是 `~/.local/bin/claude`；CLI 和扩展版本不同（2.1.299 vs 2.1.310），但**共用 `~/.claude/` 下的凭证和 settings.json** [文档+本机验证]。
- Windows 原生扩展使用 Windows 侧的配置目录，与 WSL 完全独立；本项目只覆盖 WSL。

### 1.2 账户类型 [本机验证]

- `subscriptionType: team`，`rateLimitTier: default_claude_max_5x`，组织普通成员。
- 即：这是 **Team 套餐席位，限额等级等同 Max 5x**，不是个人 Max。文档里关于 Max 的行为基本适用，但差异处要注意（见 2.1）。
- `hasExtraUsageEnabled: false`，`cachedExtraUsageDisabledReason: org_level_disabled`：官方的"额外用量 / usage credits"功能被**组织级别禁用**，普通成员自己开不了。

### 1.3 官方认证机制 [文档]

认证优先级（高→低）：Bedrock/Vertex 环境变量 → `ANTHROPIC_AUTH_TOKEN` → `ANTHROPIC_API_KEY` → `apiKeyHelper` → `CLAUDE_CODE_OAUTH_TOKEN` → claude.ai 订阅登录。

- `ANTHROPIC_API_KEY`：交互模式首次使用要确认一次（记在 `~/.claude.json` 的 `customApiKeyResponses`），`-p` 模式只要存在就直接用。**设置了它就优先于订阅**。
- `apiKeyHelper`（settings.json）：脚本输出的 key 优先于订阅登录；默认 5 分钟缓存（`CLAUDE_CODE_API_KEY_HELPER_TTL_MS`），401/403 时重跑。**脚本失败只报错，不回退到订阅**。
- settings.json **被 Claude Code 监视并热重载**，文档明确说包括 permissions、hooks 和 "credential helpers such as apiKeyHelper"。
- 没有任何官方的"订阅耗尽自动切 API Key"功能。限额命中时的官方行为：阻塞请求直到重置时间；交互模式有 **auto-continue**（等到重置后自动续跑任务），但不换账号。

### 1.4 额度信号 [文档 + 本机验证]

- **statusLine JSON** 含 `rate_limits.five_hour.{used_percentage, resets_at}` 和 `rate_limits.seven_day.{...}`（epoch 秒），窗口过期后字段消失；还含 `cost.total_cost_usd`、`session_id`、`transcript_path`、`model`、`version`。
- 文档说此字段"仅对 Pro/Max 订阅者提供"，未提 Team。**本机验证**：用 `--settings` 临时注入 statusLine 跑了一轮 haiku，拿到 `{"five_hour": {"used_percentage": 3, "resets_at": 1792935000}}`——**Team 席位也有此字段**。`seven_day` 当时未出现（可能是尚未累计或已过期）。
- 限额错误文本：`You've hit your session limit · resets 3:45pm` / `weekly limit` / `Opus limit` / `Sonnet limit`。
- Hook 事件中只有 **`StopFailure`** 对应 API 错误，matcher 含 `rate_limit`、`authentication_failed`、`billing_error` 等。订阅限额命中是否映射为 `rate_limit` **[假设]**。
- `/usage`、`/status` 是交互命令，无法脚本化读取；没有官方 CLI/API 返回剩余额度数值。
- Hook 不能修改当前会话的认证；`CLAUDE_ENV_FILE` 只影响 Claude 执行的 Bash 命令，不影响 Claude Code 自己的 API 凭证。

## 2. 可行性结论

| 需求 | 结论 |
|---|---|
| 默认 Max | 可行。保证环境中没有 `ANTHROPIC_API_KEY`，settings 里没有 `apiKeyHelper` 即可 |
| 额度耗尽检测 | 可行，基于官方 statusLine `rate_limits`（已验证）+ `StopFailure` hook 兜底 |
| 恢复检测 | 可行且无需轮询：用耗尽时记录的官方 `resets_at` 做定时判断 |
| 自动切到 API | **部分可行**。新会话/重启进程可全自动；**同一运行中会话能否不重启切换取决于 apiKeyHelper 热重载实验 [假设]** |
| 自动切回 Max | 同上 |
| WSL CLI | 可行（wrapper 自动 `--resume` 重建会话） |
| VS Code 扩展 | 读取同一 settings.json，可以吃到 apiKeyHelper 热重载；但扩展里是否执行 statusLine、是否触发 StopFailure **[假设]**；无法用脚本替它新建/恢复会话 |
| 费用硬上限 | **本地做不到硬限制**。硬限制只能靠 Anthropic Console 的 workspace 月度花费上限（官方功能）。本地只能做软限制 + 日志 |
| 完全不打断任务地切换 | **[不可行]**（在同一 HTTP 请求失败后，当前轮次必然中断；最多做到自动重建会话续跑） |

## 3. 推荐架构

核心思想：**不碰环境变量，不在 Max 模式下让任何 API Key 出现在进程环境里；用一个状态文件 + 两个官方扩展点（statusLine、apiKeyHelper）完成检测与切换。**

```text
 ~/.claude/settings.json
   ├── statusLine → claude-switch statusline   (每次响应后收到 rate_limits / cost / session_id)
   ├── hooks.StopFailure → claude-switch on-stop-failure   (rate_limit / auth 错误兜底)
   └── apiKeyHelper → claude-switch api-key   (★ 仅在 API 模式时存在；Max 模式下此键被删除)

 ~/.config/claude-switch/
   ├── state.json      mode(auto|force-max|force-api), effective(max|api), reason,
   │                   five_hour_resets_at, seven_day_resets_at, switched_at
   ├── api_key         0600，只有 helper 读
   ├── config.json     阈值：used_percentage 触发值、API 日/月软上限 USD、冷却时间
   └── log/switch.log  每次切换：时间、原因、前后模式、验证结果
       log/api-cost.jsonl  API 模式下每个会话的 total_cost_usd
```

关键组件：

1. **`claude-switch statusline`**（statusLine 命令）：读 stdin JSON → 更新 state（最新用量、resets_at、session_id、cost）→ 判断是否需要切换 → 输出一行状态给状态栏（显示当前模式和 5h/7d 用量）。
2. **`claude-switch api-key`**（apiKeyHelper）：只在 API 模式下存在于 settings.json；输出 key。失败时写日志并退出非 0。
3. **`claude-switch on-stop-failure`**（StopFailure hook）：matcher `rate_limit` 时作为耗尽兜底信号；`authentication_failed`/`billing_error` 且当前是 API 模式时立刻切回 Max 并停止自动重试。
4. **`claude-switch set-mode auto|max|api`、`status`、`log`**：手动控制与查询。
5. **切换动作**（唯一会写 settings.json 的地方）：先备份，再原子地增/删 `apiKeyHelper` 键；写 state；记日志；随后用 `claude auth status`（新进程视角）验证。
6. **恢复检测**：切到 API 时记下 `resets_at`；由 statusline 每次被调用时检查"现在 ≥ resets_at 且冷却期已过"→ 切回 Max。没有会话活动时不需要检测（没有活动就没有费用）。可选加一个 systemd user timer 作为无会话时的兜底。
7. **CLI wrapper `claude`**（可选，WSL，放 PATH 前面）：启动前读 state 决定是否允许 API 模式；进程以"命中限额"退出或 state 在运行中变为需要切换时，提示并自动 `claude --resume <session_id>`。仅在热重载实验不成立时才需要（实验结果见 docs/02，最终未实现）。

### 耗尽判定规则（避免误判）

- 主信号：statusLine `rate_limits.five_hour.used_percentage ≥ 100` 或 `seven_day ≥ 100`（阈值可配，例如 ≥ 98）。
- 兜底：`StopFailure` matcher = `rate_limit`，且最近一次 statusline 用量 ≥ 90%。单独的 `rate_limit` 错误（可能只是 API 过载 429）不触发。
- `overloaded`、`server_error`、网络错误、`unknown` 一律不触发。
- 切换后冷却 N 分钟内不反向切换，防抖。

### 费用控制

- **硬上限**：建议在 Anthropic Console 为这个 Key 单独建 workspace 并设月度 spend limit（官方，服务器端）。
- **软上限**：statusline 的 `cost.total_cost_usd` 累计到 `api-cost.jsonl`；日/月累计超阈值 → 自动切回 Max 并拒绝再进入 API 模式（需手动 `set-mode api` 解除）。软上限的粒度是"每次响应后"，一次长响应可能略超。
- API 模式下出现 `authentication_failed` / `billing_error` → 立即切回 Max，不重试。

### 密钥存储

- 不进 settings.json、不进源码、不进日志。helper 从 `~/.config/claude-switch/api_key`（0600）读；有密码管理器 CLI 的话也可以改成 `op read` 之类的方式。
- 不要把 key 放在 `.bashrc` 之类的 shell 配置里导出，那会让它出现在每个 shell 的环境里。

## 4. 双环境的具体方法与限制

### WSL CLI
- 认证切换：apiKeyHelper 增删 + wrapper 重启 `--resume`。
- 运行中会话：**[假设]** settings 热重载后下一次请求是否改用 helper 的 key，需要实验（阶段三第一步）。若成立 → 真正的同会话切换；若不成立 → wrapper 自动 `--resume` 重建（会话历史完整保留，当前被打断的那一轮需要重新发送）。
- 副作用：被打断的那一轮里已执行的工具调用不会回滚；重建后由模型根据历史继续，通常不会重复执行已完成步骤，但无法保证。

### VS Code 扩展（Remote-WSL）
- 读同一个 `~/.claude/settings.json`，apiKeyHelper 热重载若成立则扩展同样受益，无需重启。
- **[假设]** 扩展是否执行 statusLine 命令、是否触发 StopFailure hook，需验证。若不执行 statusLine，则扩展会话只能依赖 CLI 会话或 hook 产生的状态。
- 无法用脚本替扩展新建会话：若热重载不成立，扩展侧只能做到"自动切换认证 + 通知用户点一下恢复会话"。

### Windows 原生扩展
- 本项目不覆盖；若需要，脚本要用 PowerShell 重写一份，状态文件独立。

## 5. 替代方案（供对比）

| 方案 | 评价 |
|---|---|
| 开启套餐的"额外用量"（usage credits） | 官方、零开发、不中断会话，但按套餐账户计费而非独立 Key；Team 席位需要组织管理员开启 |
| 两个 `CLAUDE_CONFIG_DIR` 来回切 | 会话历史也分家，不适合 |
| 环境变量 + shell wrapper | 只对新进程有效，对扩展无效，而且 key 长期暴露在环境里 |
| 独立监控进程轮询额度 | 没有官方额度查询接口可轮询；没有会话活动时也不需要检测 |

## 6. 阶段三开始前要做的两个实验

1. **apiKeyHelper 热重载实验**：在 Max 模式下开一个 CLI 会话 → 向 settings.json 加入 apiKeyHelper（指向一个输出"无效 key"的脚本，避免真实计费）→ 发一条消息 → 看是否报 `authentication_failed`（说明已切到 helper）→ 删除该键 → 再发一条 → 看是否恢复订阅。全程不产生真实 API 费用。
2. **扩展侧 statusLine / StopFailure 实验**：在 Remote-WSL 扩展里跑一轮，看 statusline 脚本是否被调用、hook 是否触发。

两个实验的结果决定"同会话无缝切换"还是"自动重建会话"。

## 7. 恢复原环境

- 所有改动集中在：`~/.claude/settings.json` 的 `statusLine`、`hooks.StopFailure`、`apiKeyHelper` 三个键（修改前自动备份到 `~/.claude/backups/`），`~/.config/claude-switch/`，以及 PATH 里的 wrapper。
- `claude-switch uninstall`：还原 settings.json 备份、删除 wrapper 和 state；API Key 文件需用户确认后删除。
